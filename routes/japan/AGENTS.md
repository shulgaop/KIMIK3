# AGENTS.md — маршрут «Япония» (routes/japan/)

Постоянные правила работы над японским маршрутом. Основаны на утверждённом
комплектном `AGENTS.md` проекта «Гид по маршруту — Япония»; принципы не изменены,
адаптированы только фактические пути и команды.

Корневой `AGENTS.md` репозитория (Git-процесс, контракт выдачи, стандарты кода)
действует совместно с этим файлом. `route_app/AGENTS.md` описывает контракт
качества генератора и тоже обязателен при работе с общим кодом.

## 0. Привязка путей и инструментов (фактическая адаптация)

Управление японским маршрутом хранится в `routes/japan/`, чтобы не смешиваться
с документами маршрута Фанских гор в корне и `route_app/`:

- `CONTEXT.md` → `routes/japan/CONTEXT.md`
- `DECISIONS.md` → `routes/japan/DECISIONS.md`
- `TASKS/` → `routes/japan/TASKS/`
- `SOURCES.md` → `routes/japan/SOURCES.md`
- Данные, исследования, конфигурация → `routes/japan/{config,data,research,generated}/`
- `ATLAS.md`, `atlas-out/`, `scripts/atlas.py` → корень репозитория (Atlas общий,
  индексирует весь репозиторий)

Команды Atlas выполняются из корня репозитория:
`python3 scripts/atlas.py build|query|related|update|manifest|status|done|fail ...`
(в Windows — `python` вместо `python3`).

Доступность инструментов (зафиксировано 2026-11-22):

- `project-atlas`, `webapp-building`, GitHub plugin, `kimi-pdf`, `kimi-word`,
  `kimi-excel`, `kimi-webbridge`, `webapp-publish` — доступны.
- `musepool` — плагин маркетплейса, устанавливается пользователем; до установки
  визуальную систему проектировать по `webapp-building` без имитации musepool.
- `playwright-cli` — недоступен; браузерные проверки выполняются через
  `kimi-webbridge` (реальный браузер пользователя). Не имитировать.
- `website_version_manager` — недоступен; версионирование и откат публикации
  выполняются механизмом GitHub (ветки, теги, revert) и историей публикаций
  выбранной площадки. Не имитировать.

Новые Skills, plugins и сервисы не устанавливать без разрешения пользователя.

## 1. Главные принципы

1. Общий движок отделён от данных маршрутов.
2. Сначала переиспользование и конфигурация, затем — только обоснованное
   изменение общего кода.
3. История чата не является хранилищем проекта. Источник истины — файлы и Git.
4. Не выдумывать факты, файлы, проверки, commits, публикации и результаты команд.
5. Не перезаписывать исходные материалы пользователя.
6. Не создавать дубли и конкурирующие версии одного документа.
7. Любое изменение завершается проверкой и обновлением контекста и Atlas.

## 2. Обязательный порядок начала работы

1. Прочитай корневой `AGENTS.md` и этот файл.
2. Прочитай `routes/japan/CONTEXT.md` и активную задачу из `routes/japan/TASKS/`.
3. Прочитай подтверждённые решения из `routes/japan/DECISIONS.md`, если задача
   затрагивает соответствующую область.
4. Для навигации используй `ATLAS.md`; не более 2–3 точечных Atlas-запросов
   перед открытием рабочих файлов.
5. Проверь фактическое содержимое изменяемых файлов и зависимостей.
6. Только после этого продолжай согласованную задачу.

Если `CONTEXT.md` отсутствует, не выдумывай состояние: прочитай README,
`routes/japan/` и задай вопрос только о недостающем.

## 3. Ответственность файлов

- `AGENTS.md` (этот файл) — постоянные правила и контракт качества.
- `routes/japan/CONTEXT.md` — единственный операционный снимок: этап, состояние,
  блокировки, следующий шаг, ветка и ссылки; ориентировочно до 200 строк.
- `routes/japan/DECISIONS.md` — ID, дата, решение, причина, альтернативы,
  статус подтверждения.
- `routes/japan/TASKS/` — одна задача на файл: статус, критерии готовности,
  затронутые файлы, результат проверки.
- `routes/japan/SOURCES.md` — реестр источников: даты получения и проверки,
  статус учёта, область применения.
- `ATLAS.md` и `atlas-out/` — сгенерированная карта; не редактировать вручную.

Не помещай текущий прогресс в `AGENTS.md`. Не храни полные исследования в
`CONTEXT.md` — используй `routes/japan/research/` и ссылки. Не создавай файлы
`final`, `new`, `latest`, `v2` вместо обновления основного согласованного файла.

## 4. Project Atlas — обязательный протокол

Применяется в полном объёме комплектного протокола:

- Atlas — основная карта; не заменяй его повторным сканированием каталогов.
- Для концептуального поиска используй несколько синонимов (поиск лексический).
- По `headings` выбирай файл и раздел до открытия исходника.
- Перед редактированием выполни `related` для вероятных дублей и аналогов.
- После создания, изменения или удаления файлов выполни `update`; не завершай
  этап с устаревшим Atlas.
- Пакетная обработка — через manifest; `done`-файлы с неизменным content hash
  повторно не обрабатывай.
- Не индексируй и не коммить секреты и конфиденциальные материалы. В Git-проекте
  Atlas обязан использовать `git ls-files --cached --others --exclude-standard`:
  `.gitignore` — граница индексации, а не только ограничение коммитов.

## 5. Экономия контекста

1. Не читай репозиторий целиком для ориентации.
2. Не открывай соседние документы без связи с задачей.
3. Не перечитывай большие файлы, если нужный актуальный фрагмент уже установлен.
4. Не восстанавливай состояние по переписке, если есть `CONTEXT.md`, задачи и Atlas.
5. После содержательного этапа сразу обновляй файлы состояния.
6. Давай пользователю короткие промежуточные результаты: что завершено, что
   дальше, что блокирует работу.

## 6. Разделение маршрутов и данных

1. Данные Японии хранятся только в `routes/japan/`.
2. Не копируй содержимое Фанских гор в Японию.
3. Не меняй файлы маршрута Фанских гор (`app/`, `route_app/examples/Фанские_горы/`),
   кроме явно согласованной работы над общими компонентами.
4. Параметры маршрута — в `routes/japan/config/route.yaml`: даты, IANA timezone
   (`Asia/Tokyo`), bbox, языки, дни, точки, слои и источники.
5. Не наследуй от Фанских гор часовой пояс, координаты, климатические и горные
   допущения (кроме явно переиспользуемых общих вычислений движка).
6. Различай пользовательские исходники, подтверждённые факты, вычисленные
   значения, рекомендации и допущения.
7. Генерация воспроизводима из исходников и конфигурации.

## 7. Исследования и источники

1. Маршрут, билеты и бронирования пользователя — источник фактических планов.
2. Изменяемые правила, расписания, цены, ограничения и доступность проверяй по
   актуальным источникам, предпочитая официальные.
3. Для изменяемых сведений указывай источник и дату проверки в `SOURCES.md`.
4. Не выдавай старое расписание или цену за актуальные.
5. При расхождении источников фиксируй расхождение, а не выбирай значение молча.
6. Недоступные данные обозначай как непроверенные и указывай способ перепроверки.
7. Не публикуй паспортные данные, коды бронирований, личные контакты и другие
   приватные сведения.
8. Японские названия и адреса проверяй по объектам; сохраняй написание на
   японском вместе с русским/английским.
9. Отсутствие билетов, бронирований и части документов не блокирует проект:
   помечай `ожидается` и продолжай доступные работы.

### 7.1. Протокол новых источников

При каждом новом источнике:

1. Определи точное имя файла или URL; прочитай только новый материал.
2. Не изменяй исходник; не сканируй заново весь проект.
3. Зарегистрируй в `SOURCES.md`: ID, файл/URL, даты получения и проверки,
   статус (`ожидается`, `получен`, `учтён`, `конфликтует`, `устарел`), область
   влияния, примечание.
4. Файл в проектном хранилище → инкрементальный Atlas `update`. Источник только
   в материалах Work → ссылка и извлечённые сведения без переноса приватных
   данных в Git.
5. Точечные `query` и `related` для затронутых разделов.
6. Классификация: `новое`, `подтверждает`, `уточняет`, `заменяет`,
   `конфликтует`, `не относится к маршруту`.
7. Сообщи влияние на даты, ночёвки, транспорт, бюджет, карту, порядок дней,
   решения.
8. При существенном изменении или конфликте с подтверждённым решением получи
   разрешение пользователя; не меняй маршрут молча.
9. После согласования обнови только затронутые данные и разделы, повтори
   проверки.
10. Обнови `CONTEXT.md`, `TASKS/`, `DECISIONS.md`, `SOURCES.md` и Atlas.
11. Не публикуй новую версию автоматически только из-за поступления источника.

## 8. Инженерный контракт

1. Сначала решай задачу данными и конфигурацией маршрута.
2. Общие вычисления — в переиспользуемых функциях `route_app/scripts/`;
   не дублируй код между маршрутами.
3. Существующие реализации GPX/KML используй как референс; не переписывай
   без причины.
4. Не меняй общий движок сверх согласованного объёма.
5. Все вычисления — кодом: расстояния, суммы, даты, статистика, итоги.
6. Не оставляй скрытые ручные действия, необходимые для повторной генерации.
7. После изменения общего кода — регрессионная проверка Фанских гор
   (`test_regression.py` 14/14, `pyflakes` чисто).
8. Временные файлы, кэши и секреты не коммить.

## 9. География, GPX и KML

1. Расстояния, проекции точек и статистику рассчитывай скриптами.
2. Проверяй соответствие трека дням и программе; не удаляй альтернативные
   участки без согласования.
3. После генерации проверяй XML и попадание всех точек и линий в bbox
   активного маршрута (bbox Японии — из `config/route.yaml`).
4. В KML порядок координат: `долгота,широта,высота`.
5. Проверяй соответствие каждого `styleUrl` существующему `Style id`.
6. Не используй внешние ресурсы, ломающие мобильный офлайн-результат.
7. Не применяй bbox, высоты, временные сдвиги и контрольные числа Фанских гор
   к Японии.

## 10. Веб-интерфейс

1. Соблюдай `webapp-building` (и `musepool`, когда плагин установлен) до
   проектирования интерфейса.
2. Не оставляй неработающие кнопки, фильтры, ссылки, обещания функций,
   заглушки.
3. Мобильная навигация, читаемые таблицы, состояния загрузки, ошибок и пустых
   данных.
4. Критически важная информация — с согласованным офлайн-сценарием.
5. При недоступности внешней карты или сервиса интерфейс остаётся пригодным
   с предупреждением и запасным сценарием.
6. Не используй эффекты в ущерб чтению, производительности и мобильной работе.
7. Сначала один вертикальный срез маршрута, затем масштабирование наполнения.

## 11. Обязательная проверка

Наличие файла и чтение кода не являются проверкой работоспособности. Проверяй
фактически (браузерные проверки — через `kimi-webbridge`):

- браузер и мобильный viewport (iPhone);
- основные пользовательские сценарии;
- отсутствие ошибок JavaScript и битых ресурсов;
- карту, координаты, ссылки и внутренние переходы;
- офлайн-сценарий после первой загрузки;
- воспроизводимость генерации;
- печать, KML, GPX, ICS и аудиогид — по входящим в объём форматам;
- регрессионные тесты Фанских гор после изменений общего кода;
- опубликованный URL после размещения.

Ошибки, делающие результат непригодным, исправь до выдачи. Непроверенное явно
обозначь как непроверенное.

## 12. Git и публикация

1. Рабочая ветка: `feature/japan-guide`; интеграция — через Pull Request.
2. Не работай напрямую в `main`.
3. Запрещены force push, удаление истории и удаление файлов для «исправления»
   без разрешения.
4. Перед commit проверь фактический список файлов и отсутствие секретов.
5. В PR: задача, изменения, проверки, обновление контекста, риски.
6. Не заявляй о commit, push, PR, защите ветки или публикации без фактического
   подтверждения.
7. Публикация — по решению D-001: GitHub Pages из приватного репозитория
   (требуется GitHub Pro) + парольный экран в гиде; версии сохраняются с
   возможностью отката.
8. Перед публикацией проверь отсутствие приватных сведений.
9. Основной результат — проверенная ссылка, открывающаяся на iPhone.

## 13. Завершение задачи и handoff

После каждого содержательного этапа:

1. Обнови `routes/japan/CONTEXT.md` и активную задачу.
2. Зафиксируй новые подтверждённые решения в `DECISIONS.md`.
3. Обнови `SOURCES.md`, если появились новые факты.
4. Выполни Atlas `update` и проверь manifest-статусы.
5. Проверь `git status` и отсутствие секретов.
6. Укажи ветку и commit, если они существуют.

Отчёт пользователю: что сделано; что фактически проверено; что не работает или
не подтверждено; какие файлы изменены; обновлён ли Atlas; следующий шаг; какой
файл и раздел открыть следующему чату; полезные Atlas-запросы.

Задача не завершена, если результат не проверен или файлы состояния устарели.

## 14. Обязательная остановка

Остановись и задай один структурированный вопрос, если:

- не хватает критических исходных данных;
- обнаружено противоречие подтверждённых решений;
- работа выходит за согласованный объём;
- требуется изменить существующий маршрут или общий движок без утверждённого
  плана;
- требуется удаление, force push или публикация приватных данных;
- недоступны необходимые авторизация или инструмент;
- проверка выявила блокирующую ошибку.

Не продолжай на предположениях, если цена ошибки — потеря данных, нарушение
приватности или непригодный маршрут.
