## 0. ОБЯЗАТЕЛЬНОЕ ПРАВИЛО: MD-снимок проекта для продолжения в другой модели

**Всегда, на каждом этапе работы и при каждой выдаче результата, формировать и обновлять файл `СТАТУС_<Маршрут>.md`** — «передаточный» markdown, по которому ЛЮБАЯ другая модель (или вы сами через неделю в новом чате) продолжит работу без единого уточняющего вопроса. Это правило не опционально: работа считается незавершённой, пока снимок не обновлён.

Содержание снимка (структура фиксированная):
1. **Задача и входные данные:** маршрут, даты, формат, файлы пользователя (точные пути, что в них найдено: рейсы, вагоны/места, номера брони, нормы багажа).
2. **Что уже сделано:** список всех файлов выдачи с абсолютными путями и датами последнего изменения; для HTML — ID последней сохранённой версии сайта; для аудиогида — число треков и голос.
3. **Принятые решения и почему:** ключевые числа (склонение компаса, окно градиентов, выбранные источники), исправленные ошибки (что было неверно и на что заменено) — чтобы следующая модель не «откатила» исправление.
4. **Что не сделано / открытые вопросы:** запросы пользователя без ответа, ожидаемые данные (напр., адрес отеля от организатора), запланированные перепроверки (погода за N дней до старта).
5. **Как продолжить:** 3–5 конкретных следующих шагов с привязкой к разделам этой инструкции.

Правила ведения снимка:
- Обновлять **после каждого изменения файлов выдачи** (не в конце сессии — сессия может оборваться).
- Писать фактами и путями, без описаний процесса («исправлено: lat/lon в KML перепутаны → координаты приведены к lon,lat, добавлена bbox-проверка»).
- Хранить рядом с файлами выдачи; имя — на языке пользователя.
- Любая новая модель при старте читает сначала снимок, потом эту инструкцию — и только потом задаёт вопросы пользователю (в идеале — ни одного).

## 2. Разбор GPX (обязательная вычислительная часть, Python)

1. Распарсить GPX (ElementTree): отделить именованные waypoints от нумерованных точек трека (`name.isdigit()`).
2. Собрать кумулятивный километраж по гаверсинусу; снять высоты из `<ele>`.
3. **Спроецировать все ключевые точки программы на трек** (ближайшая точка): кемп, перевал, озеро → получить «км от старта» и GPS-высоту.
4. Посчитать **километраж и набор/сброс по дням** как разности проекций. Сверить с программой: карточный километраж занижен на 10–20 %, давать оба («по GPS / по программе»).
5. Посчитать **азимут движения каждого дня** между дневными точками (для ветрового анализа), перевести в румбы (С, СВ, В…).
6. Посчитать **градиенты по дням**: суммарный набор/сброс, средний набор (м/км), максимальный уклон. ⚠️ Макс. уклон — скользящим окном 300–500 м по треку (средний уклон окна), иначе GPS-шум и отвесные стены рядом с тропой дадут нереальные 50–65°. Честные значения для осыпных перевалов: устойчиво 30–40°, короткие ступени до 45°.
7. Посчитать **компасные азимуты по плечам** (между соседними ориентирами дня, не только «день в целом»): истинный, магнитный (= истинный − восточное склонение; склонение района узнать по IGRF/WMM-калькулятору на год похода) и обратный магнитный («дорога домой»). К каждому плечу — ориентиры: «перила» (река/хребет и сторона), визиры (перевальный тур, характерный пик), контрольные точки через 1–2 км (озёра, броды, чайханы), «ловушка» (объект, дальше которого идти нельзя). Плюс блок техники: работа с картой (привязка, точка атаки, целенаправленное смещение) и без карты (солнце, экспозиции склонов, коридорная навигация, обратный азимут, действия в белой пелене).
8. ⚠️ Большие GPX-кольца могут включать участки ВНЕ программы (запасные варианты) — отделить и пометить, а не удалять.

## 3. Погода, ветер, высоты — обязательный анализ

1. **Если даты дальше 10–14 дней** — точного прогноза нет: использовать климатические нормы региона и явно написать «перепроверить прогноз за N дней». Не выдумывать прогноз.
2. **Таблица температур по высотным ступеням** маршрута (не по городам!): день/ночь для каждой ночёвки. Градиент ~6 °C на 1000 м от долинной станции.
3. **Ветер:** господствующее направление региона (в Памиро-Алае — З/СЗ перенос) + дневной долинный (вверх по ущелью) / ночной горный (вниз) ветер. Сопоставить с азимутом каждого дня: встречный / попутный / боковой; где укрытие, где открытая седловина. Таблица «день → участок → азимут → эффект ветра».
4. **Правила тайминга:** перевалы — до 13:00–14:00 (грозы после полудня, усиление ветра); ключевой перевал — выход 5:00–6:00; утренние туманы — старт после рассеивания.
5. **Высотный профиль и акклиматизация:** оценить график ночёвок («пила» = хорошо), отметить ночёвки выше 3500–4000 м, симптомы горной болезни и правило «лечение — спуск», питьё 3–4 л/день, УФ (+10–12 % на км высоты).

## 4. Содержание путеводителя (структура)

1. **Шапка:** маршрут, даты, дни, км (GPS + по программе), диапазон высот, перевалы.
2. **Логистика и билеты:** рейсы (номер, время, регистрация), багаж, цепочка заброски/выброски, границы/визы, деньги (какие купюры!), связь (где есть/нет), буферные дни.
3. **Погода / ветер / высоты** — три блока из п. 3.
3.5. **Характер троп:** таблица по дням «поверхность и качество тропы (хоженость, осыпь, морена, курумник, фирн, броды, ориентирование по турам) | средний набор м/км | макс. устойчивый уклон | категория сложности (н/к, 1А, 1Б…)» + выводы по технике и снаряжению (палки, кошки, гамаши, интервалы на траверсах). Поверхность брать из отчётов по региону (tlib.ru, Wikiloc), градиенты — из п. 2.6.
4. **Маршрут по дням.** Каждый день:
   - чипы: км, набор/сброс, часы, азимут, высота ночёвки, «ключевой день»;
   - описание хода дня и тайминга;
   - **факт-блоки по точке** (см. п. 5);
   - блоки «Ночёвка», «Вода», «Опасности дня».
5. **Сводная таблица точек:** название | координаты | высота GPS | день — для Organic Maps/Maps.me/Garmin.
6. **Опасности и аварийные сходы** — таблица «риск / где / действия» + сходы по каждой трети маршрута + ближайший госпиталь + экстренные номера страны.
7. **Снаряжение — акценты:** не дублировать общую памятку, а вытащить критичное под этот маршрут и даты (температура спальника = норма самой холодной ночёвки с запасом; кошки — если фирн/снег; норма багажа авиа).
8. **KML для Google Earth** (в дополнение к GPX): LineString по каждому ходовому дню со своим цветом + Placemark-точки по категориям (лагерь, перевал, вода, чайхана, спасатели, сход) с описаниями в `<description>`; `altitudeMode` = clampToGround. **Правила корректного KML (проверено боем на мобильном Google Earth):**
   - **Порядок координат везде `долгота,широта,высота`** — и в Point, и в LineString. Ошибка «широта,долгота» переносит точки на другой континент (типичный симптом: «маршрут улетел на север»). После генерации — **автопроверка попадания всех координат в bbox региона** (например, Фаны: широта 38,9–39,6°N, долгота 67,9–68,5°E), каждая координата — и точек, и линий.
   - **ID стилей — только латиница без пробелов** (`day3`, `day10`). Кириллические ID и/или пробел на конце (`«День 3 »`) мобильный Google Earth не резолвит → линии рисуются белыми по умолчанию. После генерации проверить: каждое `styleUrl>#id` имеет существующий `<Style id>` (программно, set-сравнением).
   - **Не использовать внешние иконки** (`maps.google.com/mapfiles/...`): мобильный GE их не грузит и рисует красный «X». Оставлять стандартные метки или data-URI.
   - Цвет линий — в формате KML `aabbggrr` (не RGB!): зелёный = `ff00c832`, красный = `ff3352db` и т.п.; width 4–5 для читаемости на спутнике.
   - Финально: `ElementTree.parse` (XML валиден) + bbox-проверка + проверка styleUrl↔id.
9. **Инфраструктура маршрута:** обязательные разделы путеводителя — источники воды по дням (с пометками «последний источник перед перевалом», сезонность ледниковых ручьёв), чайханы/стационарные лагеря, пункты спасателей и медпункты (с телефонами и координатами), таблица «точки и маршруты схода» по третям маршрута + точка невозврата (главный перевал). Инфраструктуру верифицировать поиском (альплагеря, посты спасателей) — не выдумывать.
10. **Перепроверка нитки маршрута:** сверить цепочку точек программы с 1–2 независимыми отчётами (Wikiloc, tlib.ru) — отметить совпадения/расхождения и вилки (альтернативные подходы); зафиксировать дату сверки и диапазоны высот перевалов по разным источникам.
11. **Источники.**

## 5. Факт-блоки по точкам (история, география, культура, природа)

Для КАЖДОЙ точки/дня — 1–3 факт-блока с конкретикой (даты, числа, имена, этимология):
- **История:** древние города и руины, экспедиции (кто и когда первопрошёл перевал/пик), советские походные традиции, объекты ЮНЕСКО.
- **География/геология:** происхождение озёр (моренные, обвальные, ледниковые), «бараньи лбы», ледниковая «мука» и цвет воды, тектоника, стыки хребтов, высшие точки.
- **Топонимы:** перевод названий с местного языка (Куликалон — «большое озеро», Зиндон — «темница») — всегда с объяснением.
- **Флора:** реликтовые деревья (арча — возраст деревьев, охрана), эдельвейсы (не рвать — охраняются), ягоды (что можно есть), пояса растительности по высотам.
- **Фауна:** что реально увидеть в этом сезоне (сурки, улары, бородачи, горные козлы — сезон гона, эндемики типа голого османа), пастушьи собаки — с инструкцией поведения.
- **Культура и этикет:** население, язык, нормы (приветствие, хлеб, обувь, фотографирование людей), сезонные работы (отгон скота, сбор урожая), еда.
Факты **обязательно перепроверять веб-поиском** (высоты вершин и перевалов, даты, статусы ЮНЕСКО, числа вроде «1018 звёзд»); сомнительное — помечать «по отзывам/по преданию». Типичная ошибка — перепутать пик и одноимённый перевал (напр., «Казнок» — перевал 4040 м, а не вершина над лагерем): проверять, что объект существует именно в той роли, в которой подаётся.

## 6. HTML-путеводитель (открывается в Edge и любом браузере)

Назначение: чтение с экрана/печать, офлайн, без зависимостей.

**Технические требования:**
- Один самодостаточный файл `index.html` (весь CSS/JS инлайн, шрифты — системные: Georgia/serif + system sans; кириллица обязательно покрыта стеком).
- Папка проекта `/mnt/agents/output/app` с `index.html`; сохранить версию через website_version_manager, `type: "html"` — иначе предпросмотра не будет.
- Якорное оглавление (nav) по всем дням и разделам; `scroll-behavior: smooth`.
- Высотный профиль — инлайн-SVG с подписанными точками и высотами; ключевая точка (главный перевал) выделена акцентным цветом.
- Таблицы: погода по высотам, ветер по дням, точки с координатами, опасности.
- Блочная система смысловых врезок: `fact` (факты), `warn` (опасности), `tip` (советы), `audiobox` (аудиогид) — с буквицей-тегом.
- `@media print` — чистая печать (без фона, разрывы страниц между секциями); `@media (max-width:640px)` — одноколоночное оглавление.
- Дизайн: не «дефолтный AI-стиль». Перед версткой — 1 recall в musepool (запросы по проблеме: «mountain expedition field guide reading document», «longform reading hierarchy», «topographic map earth tones»), цвета — из референсов (в эталоне: шалёно-зелёная «бумага» #b0c6b3, чернильный #111, алый акцент #db3356 — «полевой журнал»).

## 7. Аудиогид (принципы написания и генерации)

**Тексты:**
- 1 трек = 1 точка/день маршрута + вводный трек (обзор: даты, километраж, высоты, главные правила). Итого 10–14 треков.
- Длительность 40–80 секунд ≈ 110–190 слов русского текста на трек.
- **Все числа — прописью** («четыре тысячи семьсот сорок метров», не «4740 м»), аббревиатуры расписаны («джи-пи-эс»).
- Живой рассказ от 2-го лица («Ты выходишь к озеру…», «Справа — стена цирка…»).
- Содержание = факт-блоки п. 5, сжатые: 1 исторический факт + 1 географический + 1 природный/культурный + 1 практический совет на точку.
- Тон: проводник рядом, а не учебник. Финальный трек — с поздравлением.

**Генерация (цепочка фолбэков):**
1. Плагин audio_generation (TTS через agent-gw). Если HTTP 424 «temporarily unavailable» →
2. `pip install edge-tts -i https://pypi.org/simple`; голос `ru-RU-DmitryNeural`, `rate="-5%"`; asyncio + `nest_asyncio` в Jupyter (event loop уже запущен); генерация батчами с retry×3 и паузами (таймаут ~120 с на пакет из 7–8 треков).
3. Сохранять mp3 в папку `Аудиогид_<Маршрут>/`.

**Контроль качества:**
- Имена файлов = названиям точек в путеводителе: «07 — Алауддинские озёра.mp3».
- Проверить каждый файл: размер >3 КБ, длительность через `ffprobe` (ожидание 40–80 с).
- Упаковать в zip, в путеводителе — раздел «Аудиогид» с расшифровкой номеров треков и советом скачать до потери связи.

## 9. Типовые грабли

- Прогноз погоды дальше 10–14 дней не существует — не выдумывать, давать климат + дату перепроверки.
- Высоты GPS против карточных расходятся на ±100 м (крутые ущелья) — давать оба, не «исправлять».
- В GPX-кольцах точка может проецироваться не на тот виток петли — проверять по соседним точкам дня.
- KML: перепутанный порядок «широта,долгота» = «маршрут улетел на север» (другой континент); кириллические ID стилей / пробел в ID = белые линии в мобильном Google Earth; внешние иконки maps.google.com = красные «X» вместо меток. Все три бага — реальные, ловить автопроверками из п. 8 раздела 4.
- Карточный километраж программ занижен на 10–20 % — основной = GPS.
- edge-tts ставится только с флагом `-i https://pypi.org/simple` (локальное зеркало неполное); в Jupyter нужен nest_asyncio; длинные тексты бить на треки, иначе таймаут.
- Плагин-TTS часто отдаёт HTTP 424 — не ждать, сразу фолбэк.
- Не забыть буферный день между финишем и обратным рейсом — проверить по билетам.

## 11. Автоматизация: скрипты и инструкции для кодовых агентов (Claude Code / Kimi Code)

Для превращения методики в приложение создан стартовый пакет **`route_app/`**:

```
route_app/
  ТЗ_приложение_генератор_горных_маршрутов.md  — черновик ТЗ (MVP F1–F6, F9; этапы; приёмка)
  CLAUDE.md        — инструкции для Claude Code (правила, структура, команды)
  AGENTS.md        — зеркальные инструкции для Kimi Code
  scripts/
    gpx_analyze.py    — разбор GPX: км (гаверсинус), высоты, проекции точек на трек,
                        плечи (набор/сброс/азимут/румб), градиенты окном 300–500 м
    make_kml.py       — KML по дням с цветами + жёсткая автовалидация
                        (XML + bbox всех координат + styleUrl↔id + запрет внешних иконок)
    make_ics.py       — календарь ICS (TZID из IANA, VALARM, экранирование текста)
    tts_audioguide.py — edge-tts батчами: голос/темп параметрами, retry×3,
                        ffprobe-проверка длительности каждого трека
```

**Правила использования пакета:**
1. Любой кодовый агент при старте читает в порядке: `СТАТУС` проекта → эту инструкцию → `ТЗ` → `CLAUDE.md`/`AGENTS.md`.
2. Все вычисления — только скриптами (раздел 2 этой инструкции); `gpx_analyze.py` — референс-реализация, её функции переиспользовать, а не переписывать.
3. После каждой генерации KML — автовалидация (она встроена в `make_kml.py`).
4. Регрессионный эталон — проект Фанов: GPX 2072 точки, 87,4 км полного кольца (~60 км программы), высоты 1533–4739 м, макс. уклоны ±40,6° окном 400 м, bbox 38.9–39.6N / 67.9–68.5E. Новые версии кода проверять сходимостью с этими числами.
5. Скрипты проверены на эталоне 27.09.2026 (gpx_analyze, make_kml — прогоном; make_ics, tts_audioguide — по шаблонам боевого проекта).

**Развитие в приложение (по ТЗ):** MVP — CLI-контур `routegen` + эти скрипты + агентные инструкции; v2 — FastAPI backend (загрузка файлов, очередь генерации, проекты в БД) + React-фронтенд (мастер входных данных → предпросмотр HTML-гида → экспорт zip). Открытые вопросы — в разделе 8 ТЗ.
